# Feature Landscape: SEO & Social Sharing

**Domain:** SEO, structured data, and social sharing for a cycling event website
**Researched:** 2026-04-09
**Milestone:** SEO & Social Sharing Polish
**Confidence:** HIGH -- verified against Open Graph protocol spec (ogp.me), Google Event structured data docs (developers.google.com), X/Twitter Card developer docs, Apple TN3156 iMessage preview spec, and current codebase inspection

---

## Context

The existing site (hiawathasrevenge.com) is a single-page Astro 6 static site for a 100-mile gravel cycling event on June 6, 2026. It already has foundational SEO/social tags in `BaseLayout.astro`:

**Already implemented:**
- `og:type`, `og:url`, `og:title`, `og:description`, `og:image` (with width/height)
- `twitter:card` (summary_large_image), `twitter:title`, `twitter:description`, `twitter:image`
- `<link rel="canonical">` with `Astro.site` base
- `<meta name="description">`
- Schema.org Event JSON-LD (name, description, startDate, endDate, eventStatus, eventAttendanceMode, location, organizer, image)
- OG image: 1200x630 JPEG generated by sharp (center-crop of hero photo)
- Favicon: SVG emoji (tree emoji in `public/favicon.svg`)
- `<html lang="en">`

**Not yet implemented:**
- `og:site_name`, `og:locale`, `og:image:alt`, `og:image:type`
- `twitter:image:alt`
- Branded/designed OG share image (current is a raw photo crop)
- `robots.txt`
- `sitemap.xml`
- Apple touch icon (180x180 PNG)
- `favicon.ico` fallback
- Web manifest (`site.webmanifest`)
- Event schema enrichments (`offers`, `description` with full detail, street-level `address`)

## Table Stakes

Features users and platforms expect. Missing any of these means the site looks unfinished or loses functionality on a major platform.

### TS-1: Branded OG Share Image (1200x630)

| Attribute | Value |
|-----------|-------|
| **Why expected** | The current OG image is a raw center-crop of the hero photo with no event name, date, or branding. When shared, the link card shows a generic forest photo -- recipients cannot tell what the event is without reading the text below. Every polished event site uses a designed card. |
| **Complexity** | Medium |
| **Platforms affected** | Facebook, iMessage, X, Discord, Slack, LinkedIn, WhatsApp, Google Discover |
| **Dependencies** | Existing `scripts/generate-og-image.js` pipeline step (replace sharp center-crop with badge/logo composite) |

**Specifications:**
- 1200x630px, JPEG or PNG, under 300KB (ideal), max 5MB
- Must include: event name ("Hiawatha's Revenge"), date ("June 6, 2026"), tagline ("A 100-Mile Gravel Ride Through the Hiawatha"), visual branding (badge/logo element)
- Keep important content (text, logo) within center 80% safe zone -- X crops to 2:1, Discord resizes to 400x300, iMessage may crop edges
- Use the site's existing shield motif or badge artwork for brand recognition
- Format: PNG recommended if text/logos are present (sharper edges than JPEG)

**iMessage note:** iMessage only reads `og:title` and `og:image` for its preview card. Title text clips at ~44 characters. The image is the primary visual -- it MUST carry the event identity on its own.

### TS-2: robots.txt

| Attribute | Value |
|-----------|-------|
| **Why expected** | Without robots.txt, search engines will crawl the site but have no guidance. More importantly, Google looks for `Sitemap:` directive in robots.txt to discover the sitemap URL. Missing robots.txt is a signal of an unfinished site to crawlers. |
| **Complexity** | Low |
| **Platforms affected** | Google, Bing, all search engines |
| **Dependencies** | None (static file in `public/`) |

**Specifications:**
```
User-agent: *
Allow: /

Sitemap: https://hiawathasrevenge.com/sitemap-index.xml
```

For a single-page public site with nothing to hide, this is trivially simple. The only purpose is to point to the sitemap and signal "come on in."

**2026 consideration:** robots.txt is now also the primary mechanism for controlling AI crawler access (GPTBot, ClaudeBot, etc.). The site owner should decide whether to allow or disallow AI training crawlers. This is a policy decision, not a technical one.

### TS-3: sitemap.xml

| Attribute | Value |
|-----------|-------|
| **Why expected** | Google and Bing use sitemaps to discover pages. For a single-page site the value is modest, but its absence is a gap in any SEO audit. The `@astrojs/sitemap` integration generates it automatically at build time. |
| **Complexity** | Low |
| **Platforms affected** | Google, Bing |
| **Dependencies** | Requires `site` in `astro.config.ts` (already set to `https://hiawathasrevenge.com`) |

**Implementation:** Add `@astrojs/sitemap` to the Astro integrations array. It auto-generates `sitemap-index.xml` and `sitemap-0.xml` at build time. For a single-page site this will contain exactly one URL.

### TS-4: Apple Touch Icon (180x180 PNG)

| Attribute | Value |
|-----------|-------|
| **Why expected** | When iOS/iPadOS users add the site to their home screen, the system looks for `apple-touch-icon.png`. Without it, iOS takes a screenshot of the page, which looks terrible. The current favicon is an SVG emoji (tree) which iOS ignores entirely for home screen icons. |
| **Complexity** | Low |
| **Platforms affected** | iOS Safari (home screen), iPadOS |
| **Dependencies** | Needs a designed 180x180 PNG (should match event branding/badge) |

**Specifications:**
- 180x180 PNG, no transparency (iOS adds rounded corners automatically)
- Place at `public/apple-touch-icon.png` (Apple looks for this path by convention)
- Add `<link rel="apple-touch-icon" href="/apple-touch-icon.png">` to head
- Should feature the event badge/shield motif, not the tree emoji

### TS-5: favicon.ico Fallback

| Attribute | Value |
|-----------|-------|
| **Why expected** | The current `favicon.svg` (tree emoji) only works in Chrome, Firefox, and Edge. Safari, some social preview crawlers, and legacy contexts look for `favicon.ico` at the root. Without it, those contexts show a generic icon or nothing. |
| **Complexity** | Low |
| **Platforms affected** | Safari, legacy browsers, RSS readers, some social crawlers |
| **Dependencies** | Needs a 32x32 (or multi-size) ICO file |

**Specifications:**
- 32x32 ICO file at `public/favicon.ico`
- Should contain 16x16 and 32x32 sizes
- Content should match the event brand (shield/badge motif), not the tree emoji
- Keep `favicon.svg` for modern browsers (it scales well and supports dark mode via CSS media queries)

### TS-6: Missing OG Meta Tags

| Attribute | Value |
|-----------|-------|
| **Why expected** | The Open Graph spec defines several tags the site is missing that affect how link previews render across platforms. |
| **Complexity** | Low |
| **Platforms affected** | Facebook, Slack, Discord, LinkedIn |
| **Dependencies** | None (add to `BaseLayout.astro` head) |

**Tags to add:**

| Tag | Value | Why |
|-----|-------|-----|
| `og:site_name` | `Hiawatha's Revenge` | Displayed alongside title in Facebook/Slack unfurls. Without it, Slack shows the bare domain. |
| `og:locale` | `en_US` | Technically optional for US English (Facebook assumes en_US), but explicit is better than implicit. Low cost, removes ambiguity. |
| `og:image:type` | `image/jpeg` (or `image/png`) | Helps crawlers skip downloading the image to detect format. Speeds up preview generation. |
| `og:image:alt` | `Hiawatha's Revenge -- A 100-mile gravel ride through Michigan's Hiawatha National Forest, June 6, 2026` | Accessibility: screen readers on social platforms use this. Twitter/X actually renders `twitter:image:alt` as img alt text. |
| `twitter:image:alt` | (same as og:image:alt) | X renders this as actual alt text on the card image. |

### TS-7: Event Schema Enrichment

| Attribute | Value |
|-----------|-------|
| **Why expected** | The existing Event JSON-LD is functional but minimal. Google's Event rich results documentation specifies required and recommended properties. Several recommended properties that improve rich result display are missing. Google also now requires a physical location with street-level address for Event rich results (as of mid-2025 update). |
| **Complexity** | Low-Medium |
| **Platforms affected** | Google Search (rich results card) |
| **Dependencies** | Existing `eventSchema` object in `BaseLayout.astro` |

**Current schema gaps:**

| Property | Status | Action |
|----------|--------|--------|
| `name` | Present | OK |
| `startDate` | Present (date only) | Should include time + timezone: `2026-06-06T06:00:00-04:00` |
| `endDate` | Present (date only) | Should include time + timezone |
| `location` | Present (city only) | Must add specific venue/start location with street address for rich result eligibility |
| `location.address.streetAddress` | Missing | Required for 2026 Event rich results |
| `location.address.postalCode` | Missing | Recommended |
| `eventStatus` | Present | OK |
| `eventAttendanceMode` | Present (OfflineEventAttendanceMode) | OK |
| `organizer` | Present | OK |
| `description` | Present | OK (could be more detailed) |
| `image` | Present (single URL) | Google recommends multiple images, min 1920px wide. Consider array with hero + OG image. |
| `offers` | Missing | Recommended. For a free event: `{"@type": "Offer", "price": "0", "priceCurrency": "USD", "availability": "https://schema.org/InStock", "url": "https://hiawathasrevenge.com"}` |
| `isAccessibleForFree` | Missing | Since it's a free ride, `true` is accurate and informative |
| `url` | Missing | Should be `https://hiawathasrevenge.com` |

**Critical 2026 update:** Google removed support for online/virtual events in mid-2025. Events must have a physical location. The current schema has `"addressLocality": "Munising"` but lacks `streetAddress`. Google may not show rich results without a street-level address.

## Differentiators

Features that are not expected but make sharing look exceptional. These go beyond "it works" to "this looks great."

### D-1: Designed Share Image with Badge/Logo Overlay

| Attribute | Value |
|-----------|-------|
| **Value proposition** | Instead of a raw photo crop, composite the event badge/shield motif, event name, date, and tagline over a scenic background photo. When someone shares the link in iMessage or Slack, it looks like an official event card -- not a random nature photo. This is what distinguishes a polished event site from a hobby page. |
| **Complexity** | Medium |
| **Platforms affected** | All (Facebook, iMessage, X, Discord, Slack, LinkedIn, WhatsApp) |
| **Dependencies** | Badge/logo artwork, sharp compositing pipeline |

**Design guidance:**
- Background: scenic photo from the route (existing hero or gallery image), desaturated or with color overlay to avoid competing with text
- Foreground: event badge/shield motif prominently placed, event name in display font, date "June 6, 2026", tagline
- Keep text within center 80% safe zone (platforms crop differently)
- Text overlay should be under 20% of total image area
- Sharp can composite SVG overlays onto photos at build time -- this replaces the current `generate-og-image.js` center-crop script

### D-2: Web App Manifest (site.webmanifest)

| Attribute | Value |
|-----------|-------|
| **Value proposition** | Enables Android "Add to Home Screen" with a proper app-like icon and name. Also provides consistent branding metadata for PWA-aware browsers. |
| **Complexity** | Low |
| **Platforms affected** | Android Chrome, Edge, Samsung Internet |
| **Dependencies** | Needs 192x192 and 512x512 PNG icons |

**Specifications:**
```json
{
  "name": "Hiawatha's Revenge",
  "short_name": "Hiawatha's Revenge",
  "description": "A 100-Mile Gravel Ride Through the Hiawatha",
  "start_url": "/",
  "display": "browser",
  "background_color": "#0a1a0a",
  "theme_color": "#0a1a0a",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

### D-3: theme-color Meta Tag

| Attribute | Value |
|-----------|-------|
| **Value proposition** | Colors the browser chrome (address bar) on mobile browsers to match the site's dark forest theme. Small touch that makes the site feel immersive and branded. Also used by some social platforms for accent color in link previews. |
| **Complexity** | Low |
| **Platforms affected** | Chrome Android, Safari iOS (status bar), Edge |
| **Dependencies** | None |

**Implementation:**
```html
<meta name="theme-color" content="#0a1a0a">
```

Use the site's `forest-900` or `forest-950` color value.

### D-4: SportsEvent Schema Type (Instead of Event)

| Attribute | Value |
|-----------|-------|
| **Value proposition** | Schema.org defines `SportsEvent` as a subtype of `Event`. Using `SportsEvent` with `sport: "Cycling"` gives Google more precise semantic information. While Google's Event rich results don't currently distinguish SportsEvent visually, the richer typing improves entity understanding for AI-powered search and knowledge graph inclusion. |
| **Complexity** | Low |
| **Platforms affected** | Google Search, AI search (Gemini, SGE), knowledge panels |
| **Dependencies** | Existing Event JSON-LD (change `@type` from `Event` to `SportsEvent`, add `sport` property) |

**Caution:** Verify that Google's Rich Results Test still validates `SportsEvent` for Event rich results. SportsEvent is a schema.org type that Google has historically supported, but the March 2026 structured data update tightened requirements. Test before deploying.

### D-5: SVG Favicon with Dark Mode Support

| Attribute | Value |
|-----------|-------|
| **Value proposition** | The current `favicon.svg` is a tree emoji. Replace it with the shield/badge motif SVG that adapts to light/dark mode via CSS `prefers-color-scheme` media query inside the SVG. The favicon visually matches the event brand and adapts to user preferences. |
| **Complexity** | Low |
| **Platforms affected** | Chrome, Firefox, Edge (tab icon) |
| **Dependencies** | Shield motif SVG already exists as `#shield-motif` symbol in BaseLayout |

**Implementation pattern:**
```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 32 32">
  <style>
    path { fill: #d4a44a; }
    @media (prefers-color-scheme: dark) {
      path { fill: #e8c872; }
    }
  </style>
  <path d="..." />
</svg>
```

## Anti-Features

Features to explicitly NOT build. Common mistakes in the SEO/social sharing domain that waste effort or cause harm.

### AF-1: Do NOT Add Multiple Schema Types for the Same Content

| Why tempting | SEO articles suggest adding Organization, WebSite, WebPage, BreadcrumbList, and Event schema to "maximize coverage." |
|--------------|---|
| **Why avoid** | Google's 2026 structured data guidance emphasizes quality over quantity. Adding schema types that don't match the primary page content can trigger manual action reviews. For a single-page event site, `Event` (or `SportsEvent`) is the correct type. Adding `WebSite` search action schema or `BreadcrumbList` to a single-page site is nonsensical. Adding `Organization` for MBTN is fine only if MBTN's details are genuinely presented on the page. |
| **What to do instead** | One well-structured Event/SportsEvent JSON-LD block. The existing `organizer` property already nests Organization info correctly. |

### AF-2: Do NOT Keyword-Stuff the Meta Description

| Why tempting | It feels like the meta description should contain every relevant keyword: "gravel cycling event Michigan Upper Peninsula Hiawatha National Forest 100 mile ride June 2026 free registration Munising MBTN trail..." |
|--------------|---|
| **Why avoid** | Google frequently rewrites meta descriptions that look keyword-stuffed. The description should read naturally because it appears in link previews on every social platform. Keyword density above natural language patterns increases bounce rates by 34%. |
| **What to do instead** | Write a compelling, natural 150-160 character description: "A free 100-mile gravel ride through Michigan's Hiawatha National Forest on June 6, 2026. Supporting the Munising Bay Trail Network." |

### AF-3: Do NOT Use og:type "event" Instead of "website"

| Why tempting | The page IS about an event, so `og:type` should be `event`, right? |
|--------------|---|
| **Why avoid** | The Open Graph `event` type requires additional properties (`event:start_time`, `event:end_time`) from Facebook's deprecated event protocol. Facebook's event type was designed for Facebook Events, not arbitrary event websites. Using `og:type` = `website` is correct for a general website about an event. The Event structured data in JSON-LD is the proper way to communicate event semantics to Google. These are separate systems. |
| **What to do instead** | Keep `og:type` = `website` (already correct). Use JSON-LD for event structured data (already implemented). |

### AF-4: Do NOT Create Separate Pages Just for SEO

| Why tempting | "We should have /about, /route, /gallery, /register pages so each can have its own meta tags and rank independently." |
|--------------|---|
| **Why avoid** | The site's editorial strength is its single-page storytelling flow. Creating thin pages that duplicate content across routes would dilute the single authoritative URL's link equity, create duplicate content problems, and break the editorial experience. A single-page site with one strong URL performs better than five thin pages in 2026's quality-focused algorithms. |
| **What to do instead** | Keep the single-page architecture. Use fragment identifiers (`#route`, `#gallery`) for internal navigation (already implemented). The canonical URL stays `https://hiawathasrevenge.com`. |

### AF-5: Do NOT Add JSON-LD for Online/Virtual Event Attendance

| Why tempting | The existing schema already has `eventAttendanceMode: OfflineEventAttendanceMode`, so this isn't currently a problem. But someone might think adding `MixedEventAttendanceMode` would help capture more search traffic. |
|--------------|---|
| **Why avoid** | Google explicitly removed online event support from Event rich results in mid-2025. Adding online attendance mode will either be ignored or could invalidate the entire Event rich result. This is a physical event. |
| **What to do instead** | Keep `OfflineEventAttendanceMode` (already correct). |

### AF-6: Do NOT Use WebP for the OG Image

| Why tempting | The site already uses WebP for hero images and thumbnails, and it's smaller. |
|--------------|---|
| **Why avoid** | While WebP support is near-universal in browsers, social platform crawlers have inconsistent WebP support. Facebook, iMessage, and some Slack clients may fail to render WebP OG images. The OG protocol spec recommends JPEG or PNG. |
| **What to do instead** | Use JPEG for photo-heavy OG images, PNG if the image has text/logos with sharp edges. The current JPEG approach is correct. If switching to a badge/logo composite design, PNG may be better for text crispness. |

### AF-7: Do NOT Place Meta Tags After Large Inline CSS/JS

| Why tempting | Astro's font preloading and inline CSS may push content into the `<head>` before meta tags. |
|--------------|---|
| **Why avoid** | Slack's unfurling crawler only reads the first 32KB of HTML response. If meta tags are pushed beyond that boundary by large inline styles, Slack will not find them and will render a blank or broken preview. |
| **What to do instead** | Ensure OG and Twitter meta tags appear early in `<head>`, before any large inline blocks. In the current `BaseLayout.astro`, meta tags are positioned after charset/viewport but before fonts and preloads -- this is correct. Verify this ordering is maintained after any future refactoring. |
