# Phase 16: Masonry Gallery - Research

**Researched:** 2026-03-31
**Domain:** CSS columns masonry layout, featured photo sizing, PhotoSwipe 5 integration
**Confidence:** HIGH

## Summary

The existing `PhotoGallery.astro` is a simple uniform grid (`grid-cols-2 sm:grid-cols-3 lg:grid-cols-4`) using `aspect-square object-cover` which crops all photos to squares. The redesign replaces this with CSS columns masonry so photos display at their natural aspect ratios. PhotoSwipe 5.4.4 is already integrated and working — the lightbox just needs its gallery container selector updated, not a reinstall or restructure.

The critical finding for this phase: **CSS columns (`column-count`) does not support items spanning a specific number of columns** — only `column-span: all` is widely supported, which collapses the masonry flow by forcing full-width interruptions. This makes "featured photos at larger sizes" a layout design decision, not a simple CSS property. The planner must choose an approach for featured photo treatment.

The photos.json data has **no `featured` field** today — neither in `photos-manifest.json` nor in `photos.json`. Adding `featured: true` requires (1) editing `photos-manifest.json` manually and (2) updating `match-photos.js` to pass the field through to `photos.json`. The 54 photos are 94% portrait (1536x2048), 4 landscape (2048x1536), 1 tall narrow (1152x2048).

**Primary recommendation:** Use Tailwind's `columns-1 sm:columns-2 lg:columns-3` with `break-inside-avoid` on items. For featured photo treatment, use `column-span: all` with `break-inside: auto` overridden — this creates a full-width photo that breaks the column flow but creates a natural editorial pause. Alternatively, make featured photos simply taller/wider within their column via aspect ratio or max-height rules rather than spanning columns.

### Pattern 1: CSS Columns Masonry Container

**What:** Use Tailwind `columns-*` utilities for responsive column-count. Items use `break-inside-avoid` to prevent splitting across columns.

**When to use:** Always — this is the locked approach per REQUIREMENTS.md.

**CSS properties used:**
- Container: `column-count` (via Tailwind `columns-1`, `columns-2`, `columns-3`)
- Container: `column-gap` (via Tailwind `gap-*` — but see Pitfall #1 below)
- Items: `break-inside: avoid` (via Tailwind `break-inside-avoid`)
- Items: `margin-bottom` for vertical spacing between items within a column
- Items: `display: inline-block` OR `width: 100%` to prevent items from bridging columns

**Exact Tailwind classes for responsive masonry container:**
```html
<div id="photo-gallery"
     class="columns-1 sm:columns-2 lg:columns-3 gap-3">
  <!-- items -->
</div>
```

**Item classes:**
```html
<a class="block mb-3 break-inside-avoid overflow-hidden">
  <img class="w-full h-auto" />
</a>
```

**Source:** Tailwind v4 docs (tailwindcss.com/docs/columns), MDN CSS multi-column layout

### Pattern 2: Natural Aspect Ratios (No Square Crops)

**What:** Replace `aspect-square object-cover` with `w-full h-auto`. Images render at their natural dimensions.

**Why this matters:** The 54 photos are mostly 1536x2048 portrait (3:4). Removing the square crop means each photo takes ~33% more vertical space in the column. This is the desired masonry visual — columns fill at different rates, creating the staggered appearance.

**Implementation:**
```html
<img
  src={photo.thumb}
  alt=""
  loading="lazy"
  decoding="async"
  class="w-full h-auto block"
/>
```

The `data-cropped="true"` attribute on the anchor tag must be **removed** (it's currently set to `true`, which tells PhotoSwipe the thumbnail is cropped for zoom animation alignment — with natural aspect ratios, this is no longer accurate).

### Pattern 3: Featured Photo Treatment Options

**Critical constraint:** CSS `column-span` only reliably supports `none` and `all`. Numeric values (`column-span: 2`) are in the spec (CSS Multi-column Level 2) but NOT widely supported in 2026.

**Option A: `column-span: all` (Full-width interruption)**
- Featured photo spans all columns
- Breaks the column flow above and below it — content before and after the featured item each form their own column blocks
- Creates an "editorial moment" — full-width hero photo in the gallery stream
- Drawback: interrupts masonry flow, prevents columns from filling smoothly
- Implementation: `column-span: all` on the `<a>` element for featured photos

**Option B: Taller within column (Recommended)**
- Featured photos render at natural aspect ratio within a column but are not artificially constrained
- Since featured photos are the same width as all other photos in the column, "larger" means taller (more natural height for landscape or very tall portrait photos)
- No special CSS needed beyond `h-auto` — the natural photo dimensions drive height
- This approach IS the masonry behavior: items naturally vary in height
- Add a subtle visual treatment (amber border, caption overlay) to distinguish featured photos

**Option C: Double-width in a nested grid (Flowbite pattern)**
- Switch container to CSS Grid with 2/3 columns, mark featured with `col-span-2`
- Requires abandoning `column-count` approach
- Out of scope per REQUIREMENTS.md (CSS Grid masonry is excluded; CSS columns is the chosen approach)

**Recommendation for planner:** Use Option A (`column-span: all`) for 2-4 featured photos. The full-width treatment creates clear editorial hierarchy. The flow interruption is intentional — a featured photo functions as a visual divider. Alternatively, if the user wants masonry to remain uninterrupted, use Option B and distinguish featured photos only with visual styling (border, label, or caption).

### Pattern 4: PhotoSwipe Integration with CSS Columns

**Key finding (verified in PhotoSwipe 5.4.4 source):** PhotoSwipe uses `querySelectorAll` (via `getElementsFromOption`) to collect child elements. CSS columns does NOT reorder DOM elements — it only changes visual positioning. Therefore, **slide index order = DOM order = photos.json array order**. The existing `map:photoClick` bridge using `photoIndex` (the index from `photosData.forEach`) will remain correct because the DOM order of `<a>` elements in the gallery matches the photos array order.

**What must change in the PhotoSwipe init:**
1. Remove `data-cropped="true"` from all `<a>` elements (or only add it to featured photos if they have cropped thumbnails)
2. The `gallery: '#photo-gallery'` and `children: 'a'` selectors remain unchanged
3. The `map:photoClick` bridge in the `<script>` block remains unchanged

**What stays the same:**
- `data-pswp-width` and `data-pswp-height` attributes (still needed, still derived from filename)
- `pswpModule: () => import('photoswipe')` dynamic import
- `lightbox.loadAndOpen(e.detail.photoIndex, { gallery: ... })` call

**If using `column-span: all` for featured photos:** The featured `<a>` element is still a direct child of the gallery container. PhotoSwipe's `querySelectorAll('a')` on the container will still find it in DOM order. No special handling needed.

### Pattern 5: Featured Field Data Pipeline

**Current state:** `photos-manifest.json` has only `filename` and `mile` fields. `match-photos.js` does not pass through any other fields. `photos.json` has only `id`, `filename`, `thumb`, `mile`, `lat`, `lon`.

**Required changes to support `featured: true`:**

1. **`public/data/photos-manifest.json`**: Add `"featured": true` to 2-4 chosen entries
2. **`scripts/match-photos.js`**: Pass the field through:
   ```javascript

     mile: snap.miles,
     lat: snap.lat,
     lon: snap.lon,
     ...(entry.featured ? { featured: true } : {}),  // pass-through
   };
   ```
3. **`PhotoGallery.astro`**: Update TypeScript type and use the field:
   ```typescript
   type PhotoEntry = {
     id: string;
     filename: string;
     thumb: string;
     mile: number;
     lat?: number;
     lon?: number;
     featured?: boolean;   // add this
   };
   ```

**Which photos to feature:** Currently no guidance. The planner should recommend marking 2-4 landscape photos (the 4 photos with 2048x1536 dimensions) as featured, since they will stand out naturally in a portrait-dominant gallery. Manual selection by the developer is expected.

### Anti-Patterns to Avoid

- **`aspect-square object-cover` on masonry images:** Destroys the entire point of masonry — natural aspect ratios are the goal
- **`column-span: 2` on featured photos:** NOT widely supported, will silently fail in most browsers
- **`grid-template-rows: masonry`:** Excluded by requirements — zero stable browser support
- **Adding `display: flex` or `grid` to the gallery container:** Breaks `column-count` — use `columns-*` not flex/grid on the container
- **Forgetting `mb-3` (or equivalent margin-bottom) on items:** Without bottom margin, items within a column stack with no gutter. Note that `gap-*` on a `columns-*` container only sets `column-gap` (horizontal), NOT row gap — vertical spacing between items must use margin-bottom on each item
- **Keeping `data-cropped="true"` on all anchors:** With `h-auto` images, the thumbnail is no longer cropped so the zoom animation origin hint is inaccurate
- **Removing `break-inside-avoid` from featured column-span items:** A `column-span: all` item does not need `break-inside-avoid` (it's not splitting across columns), but regular items do

## Common Pitfalls

### Pitfall 1: `gap-*` Only Sets column-gap in CSS Columns

**What goes wrong:** Developer adds `gap-3` to the masonry container expecting both horizontal and vertical gutters between photos.
**Why it happens:** On a `columns-*` container, `gap` only affects `column-gap` (space between columns), not the space between items stacked vertically in the same column.
**How to avoid:** Add `mb-3` (margin-bottom) to each `<a>` item element for vertical spacing. Keep `gap-3` for horizontal column gaps.
**Warning signs:** Photos touching vertically (no gap between stacked images) while column gaps are correct.

### Pitfall 2: `break-inside-avoid` Missing from Items

**What goes wrong:** Photos split across column boundaries — the top half of a photo appears at the bottom of one column, the bottom half at the top of the next.
**Why it happens:** `column-count` layouts were designed to break text across columns. Images are treated as inline content that can be fragmented.
**How to avoid:** Apply `break-inside-avoid` (Tailwind: `break-inside-avoid`) to every `<a>` item in the gallery. Also ensure `display: block` or `inline-block` on items.
**Warning signs:** Photos visually cut in half at column boundaries.

### Pitfall 3: `column-span: all` Interrupts Masonry Flow

**What goes wrong:** Adding `column-span: all` to featured photos creates abrupt full-width breaks that prevent the columns above and below from sharing a contiguous masonry flow.
**Why it happens:** `column-span: all` forces a new multi-column block context above and below the spanning element. Columns before the featured item are balanced separately from columns after it.
**How to avoid:** Accept this as the design behavior OR use a visual-only treatment (border, overlay) for featured photos instead of column-span.
**Warning signs:** Short, uneven column blocks appearing above and below featured photos with obvious white space imbalance.

### Pitfall 4: `data-cropped="true"` Left on Anchors

**What goes wrong:** PhotoSwipe's zoom-from-thumbnail animation uses `data-cropped="true"` to know the thumbnail shows only a portion of the full image. With natural-ratio thumbnails, the hint is wrong and zoom animations may look off.
**Why it happens:** The attribute was set in the original grid implementation where `aspect-square object-cover` cropped every thumbnail.
**How to avoid:** Remove `data-cropped="true"` from all `<a>` elements (or only add it where thumbnails are genuinely cropped).

### Pitfall 5: `featured` Field Not Propagated Through Pipeline

**What goes wrong:** Developer adds `"featured": true` to `photos-manifest.json` but `photos.json` doesn't include the field because `match-photos.js` doesn't pass it through.
**Why it happens:** `match-photos.js` explicitly constructs a fixed-schema output object and ignores extra manifest fields.
**How to avoid:** Update `match-photos.js` to spread or explicitly pass the `featured` field. Regenerate photos.json by running `npm run pipeline`.
**Warning signs:** `photo.featured` is always `undefined` in the Astro component even after adding to manifest.

### Pitfall 6: Map:photoClick Index Mismatch

**What goes wrong:** Clicking a map marker opens the wrong photo in the lightbox.
**Why it happens:** `RouteMap.astro` dispatches `photoIndex` based on the index in `photosData.forEach`. If photos.json order changes between pipeline runs, the map markers and gallery will fall out of sync.
**How to avoid:** The photos in `photos.json` are in the same order as `photos-manifest.json` (pipeline preserves order). Don't sort or reorder photos in `PhotoGallery.astro` without also reordering the data fed to the map. The gallery `<a>` elements must appear in the same order as photos.json.
**Warning signs:** Map marker click opens a different photo than the one marked on the map.

```html
          src={photo.thumb}

          loading="lazy"

    );
  })}
</div>
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `grid-template-rows: masonry` | CSS columns (`column-count`) | Still experimental in 2026 | CSS columns is the stable fallback |
| `display: masonry` / `display: grid-lanes` | CSS columns | CSS WG debating spec in 2025 | No stable implementation; CSS columns remains the correct choice |
| `column-span: 2` (integer) | `column-span: all` or visual-only treatment | Integer span: CSS Multi-col Level 2, not yet widely shipped | Can only span ALL columns or no columns in production |

**Deprecated/outdated:**
- `grid-template-rows: masonry`: Firefox Nightly only + Chrome flag — confirmed not stable as of March 2026
- `break-inside: avoid-page`: Print-only; use `break-inside-avoid` or `break-inside-avoid-column` for multi-column

## Open Questions

1. **Which photos should be featured?**
   - What we know: 4 photos are landscape (2048x1536), rest are portrait. No `featured` field exists yet.
   - What's unclear: No editorial guidance on which specific photos should be featured heroes.
   - Recommendation: Mark the 4 landscape-orientation photos as `featured: true` in `photos-manifest.json` as a starting point. Developer can adjust.

2. **column-span: all vs. visual-only for featured treatment**
   - What we know: `column-span: all` is widely supported and creates a full-width break. It interrupts masonry flow above/below the element.
   - What's unclear: Which visual treatment the developer prefers.
   - Recommendation: Plan a `column-span: all` implementation (Option A) as the default, with the note that it can be replaced with a visual-only treatment (border/overlay) if the flow interruption is disliked after review.

3. **Thumbnail quality for natural-ratio display**
   - What we know: Existing thumbnails are stored as WebP in `/thumbs/` and generated by `generate-thumbnails.js`. Currently displayed at square crop — they may be sized/optimized for square display.
   - What's unclear: The thumbnail dimensions. If thumbnails are generated at a fixed small square, they may appear low-res when displayed at full natural height in the masonry layout.
   - Recommendation: Check `generate-thumbnails.js` to verify thumbnail output dimensions before finalizing the plan.
