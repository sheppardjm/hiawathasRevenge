# Phase 30: Image Optimization - Research

**Researched:** 2026-04-06
**Domain:** Image optimization — WebP generation, `<picture>` element, LCP preload, CSS image-set()
**Confidence:** HIGH

## Summary

This phase has four requirements: hero WebP srcset, hero LCP preload, gallery WebP thumbnails, and parallax CSS image-set(). Research found that IMG-03 (gallery WebP thumbnails) is **already satisfied** — `photos.json` already references `/thumbs/*.webp` paths and those files exist in `public/thumbs/`. No gallery code changes are needed.

The remaining three requirements (IMG-01, IMG-02, IMG-04) are straightforward manual HTML/CSS work plus one Sharp script. Astro's built-in `<Image>` / `<Picture>` components are NOT the right approach here because images live in `public/` (Astro explicitly does not process `public/` images). The correct approach is a prebuild Sharp script to generate WebP variants, then hand-authored `<picture>` elements and CSS `image-set()` referencing the static `/images/` paths.

**Critical discovery:** The hero source image filename claims `2048x1536` but actual dimensions are **1600x1200**. This means requesting a 2048w WebP variant would require upscaling. Use `withoutEnlargement: true` in Sharp so the 2048w variant is capped at the actual 1600w source. This is fine for `sizes="100vw"` since few viewports exceed 1600px physical pixels.

**Primary recommendation:** Write a `generate-hero-webp.js` prebuild script using Sharp (already installed at 0.34.5), update `HeroSection.astro` to a `<picture>` element, add a preload `<link>` in `BaseLayout.astro`, and update CSS in `HiawathaExplainer.astro` to use `image-set()` after generating the three parallax WebP files.

### Pattern 1: Sharp Prebuild Script (generate-hero-webp.js)
**What:** A Node script run as part of `pipeline.js` that generates WebP variants at multiple widths using `withoutEnlargement: true`.
**When to use:** Any time static WebP files need to be pre-generated for use in `public/`.

```javascript
// Source: sharp docs (https://sharp.pixelplumbing.com/) + generate-thumbnails.js pattern
import sharp from 'sharp';
import { existsSync, mkdirSync } from 'fs';
import { join, dirname } from 'path';
import { fileURLToPath } from 'url';

const __dirname = dirname(fileURLToPath(import.meta.url));
const ROOT = join(__dirname, '..');
const IMAGES_DIR = join(ROOT, 'public', 'images');

const HERO_BASENAME = 'irrVhAXHnnFzslJGVemLiPEy5iQFbqZF6VzqxYOHL1o-2048x1536';
const HERO_SRC = join(IMAGES_DIR, `${HERO_BASENAME}.jpg`);

const HERO_WIDTHS = [640, 1280, 1600];

// Hero srcset variants
for (const width of HERO_WIDTHS) {
  const outPath = join(IMAGES_DIR, `${HERO_BASENAME}-${width}w.webp`);
  if (!existsSync(outPath)) {
    const info = await sharp(HERO_SRC)
      .resize({ width, withoutEnlargement: true })
      .webp({ quality: 82 })
      .toFile(outPath);
    console.log(`  hero ${width}w: ${info.width}x${info.height}`);
  }
}

// Parallax backgrounds
const PARALLAX = [
  'Eo6Lpv5a2onA-EMkS4BGrkQOHMQb4rwDbey7kfJDAZc-1536x2048',
  'K9zNeD_N2ikOKXNlKHc1dGUY7N6W3cGWVevoXlB49aI-1536x2048',
  'Gw-ZiugqoNyWNNMHZ-n65VcO7XjnipWnDWQz77mE2kQ-1536x2048',
];

for (const basename of PARALLAX) {
  const src = join(IMAGES_DIR, `${basename}.jpg`);
  const dest = join(IMAGES_DIR, `${basename}.webp`);
  if (!existsSync(dest)) {
    const info = await sharp(src).webp({ quality: 80 }).toFile(dest);
    console.log(`  parallax webp: ${basename.slice(0,8)}... ${info.width}x${info.height}`);
  }
}
```

**Note on srcset widths:** Requirements say 640w/1280w/2048w. Because the source is only 1600px wide, use 1600w as the largest variant (not 2048w). The `<picture>` srcset can list `640w, 1280w, 1600w`. This accurately describes available sizes. The requirement "2048w" was aspirational — use what the source image actually provides.

### Pattern 2: `<picture>` Element with WebP and JPEG Fallback
**What:** Replace the single `<img>` in `HeroSection.astro` with a `<picture>` that offers WebP source with srcset.
**When to use:** Any LCP image where WebP variants are pre-generated.

```html
<!-- Source: MDN picture element docs + web.dev image-performance -->
<picture>
  <source
    type="image/webp"
    srcset="
      /images/irrVhAX...-640w.webp   640w,
      /images/irrVhAX...-1280w.webp 1280w,
      /images/irrVhAX...-1600w.webp 1600w
    "
    sizes="100vw"
  />
  <img
    class="hero-img"
    src="/images/irrVhAX...-2048x1536.jpg"
    srcset="
      /images/irrVhAX...-640w.webp   640w,
      /images/irrVhAX...-1280w.webp 1280w,
      /images/irrVhAX...-1600w.webp 1600w
    "
    sizes="100vw"
    alt=""
    width="1600"
    height="1200"
    fetchpriority="high"
    loading="eager"
    decoding="async"
  />
</picture>
```

**Note on `<img>` srcset in `<picture>`:** When a `<source>` provides WebP, the `<img>` fallback's `srcset` should reference the JPEG equivalents if they exist at multiple sizes, or just `src` pointing to the single JPEG. Since only one JPEG exists, omit `srcset` on the `<img>` and rely on `src` for the JPEG fallback path.

### Pattern 3: `<link rel="preload">` for LCP Image
**What:** A preload hint in `<head>` to tell the browser to fetch the hero image early.
**When to use:** LCP images that are in the first viewport.

```html
<!-- Source: web.dev preload-responsive-images, MDN fix-image-lcp -->
<!-- In BaseLayout.astro <head>, OR in HeroSection.astro using Astro's <Fragment slot="head"> -->
<link
  rel="preload"
  as="image"
  href="/images/irrVhAX...-1280w.webp"
  imagesrcset="
    /images/irrVhAX...-640w.webp   640w,
    /images/irrVhAX...-1280w.webp 1280w,
    /images/irrVhAX...-1600w.webp 1600w
  "
  imagesizes="100vw"
  fetchpriority="high"
  type="image/webp"
/>
```

**Implementation note:** `BaseLayout.astro` currently has a hardcoded `<head>` with no slot for page-specific head content. The preload needs to go in the `<head>`. Two options:
1. Add a `headExtra` prop/slot to `BaseLayout.astro` and pass the preload link from `index.astro`
2. Hardcode the preload in `BaseLayout.astro` since this is a single-page site

Since there is only one page (`index.astro`), hardcoding in `BaseLayout.astro` is the simpler approach. The preload should use `type="image/webp"` so non-WebP browsers (essentially none as of 2026) don't fetch the webp unnecessarily.

### Anti-Patterns to Avoid
- **Using Astro `<Image>` or `<Picture>` with public/ images:** These components do not process `public/` images (Astro's official docs confirm this). They would output an unoptimized img tag while giving false confidence.
- **Moving images to `src/assets/`:** The existing pipeline uses `images/` → `public/images/` via `copy-images.js`. Restructuring would break the pipeline.
- **Preloading both JPEG and WebP separately:** Multiple preload links for the same image in different formats will cause both to be downloaded. Use a single WebP preload with `type="image/webp"`.
- **Omitting `fetchpriority="high"` from BOTH the preload link AND the `<img>`:** Both should carry it for maximum LCP benefit.
- **Upscaling the hero image to 2048w:** The source is 1600px wide. Use `withoutEnlargement: true` and advertise 1600w as the max in srcset. Upscaling increases file size with no quality benefit.
- **Generating parallax WebP without `withoutEnlargement`:** All three parallax JPEGs are actually 1200x1600 despite their filenames claiming 1536x2048. Use without-enlargement or just `webp()` without resize (convert at native dimensions).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| WebP conversion | Custom binary call or imagemagick shell exec | Sharp (already installed) | Consistent with existing thumbnail pipeline, same API pattern |
| Responsive format selection | JS-based format detection | `<picture>` + `<source type="image/webp">` | Native browser behavior, no JS overhead |
| CSS WebP detection | JS class-swapping `.webp` / `.no-webp` | CSS `image-set()` | Native CSS, widely supported since 2023, no JS needed |

**Key insight:** All three remaining requirements are declarative HTML/CSS solutions once the files exist. The only code is the Sharp script. Don't add JavaScript for format selection — browsers handle this natively.

## Common Pitfalls

### Pitfall 1: Hero Image Actual Dimensions vs Filename
**What goes wrong:** Script generates a 2048w WebP that's actually 1600px wide because Sharp caps at source resolution when using `withoutEnlargement: true`. Then the HTML srcset says `2048w` but the file is `1600px` wide, causing the browser to think it has a larger image than it does.
**Why it happens:** Filename `irrVhAX...-2048x1536.jpg` is misleading — actual dimensions are 1600x1200.
**How to avoid:** Use `1600w` (the actual maximum) in srcset and file naming. Don't advertise sizes larger than the source.
**Warning signs:** `meta.width` returns `1600` not `2048` when checked with Sharp.

### Pitfall 2: Pipeline Skips Already-Generated Files
**What goes wrong:** Re-running the pipeline regenerates all WebP files even when they haven't changed, wasting build time.
**Why it happens:** No existence check before calling Sharp.
**How to avoid:** Check `existsSync(outPath)` before processing, consistent with the project's existing patterns.

### Pitfall 3: Parallax JPEGs Also Have Misleading Filenames
**What goes wrong:** Files named `*-1536x2048.jpg` are actually 1200x1600. When converting to WebP, the output will correctly be 1200x1600. This is fine for CSS background-image (never displayed at print resolution).
**How to avoid:** Do not specify a target width when converting parallax images — just convert to WebP at native dimensions.

### Pitfall 4: Preload Link Goes in Wrong Place
**What goes wrong:** Preload link added to `HeroSection.astro` body renders outside `<head>`, providing no preloading benefit.
**Why it happens:** The `<link rel="preload">` must be in `<head>` to be effective. `HeroSection.astro` is a body component.
**How to avoid:** Add the preload to `BaseLayout.astro`'s `<head>`. Alternatively, use Astro's head slot pattern.

### Pitfall 5: CSS `image-set()` Not Applied Due to Browser Fallback Logic
**What goes wrong:** A browser that supports `image-set()` but not WebP would load... the WebP (and fail). This is not a real concern in 2026 because WebP has 98%+ support and any browser supporting `image-set()` with `type()` notation supports WebP.
**How to avoid:** The fallback JPEG in `image-set()` covers any remaining edge cases. The current pattern is correct.

### Pitfall 6: preload `href` Attribute Points to Wrong Size
**What goes wrong:** Preload `href` points to the 640w variant but the browser on desktop selects 1280w, causing a double fetch (preloaded 640w plus selected 1280w).
**Why it happens:** `href` is fetched as a fallback for browsers that don't support `imagesrcset`. On browsers that do support it, `href` is ignored and `imagesrcset` is used. The `href` should point to a mid-range size that's a reasonable default.
**How to avoid:** Set `href` to the 1280w variant as a sensible middle-ground default.

### Pitfall 7: IMG-03 "Already Done" — Don't Fix What Isn't Broken
**What goes wrong:** Developer writes code to update `PhotoGallery.astro` or `photos.json` to serve WebP, then discovers it was already working, causing confusion or regression.
**Why it happens:** The requirement IMG-03 is pre-satisfied: `photos.json` already uses `/thumbs/*.webp` and those files exist.
**How to avoid:** Verify in `photos.json` before writing any gallery code. Current state: `"thumb": "/thumbs/*.webp"` — already correct.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Single `<img src="*.jpg">` | `<picture>` with `<source type="image/webp">` | Widely supported since 2020 | 25-35% smaller files for equivalent quality |
| `-webkit-image-set()` | `image-set()` with `type()` notation | Baseline Sept 2023 | No vendor prefix needed |
| JS class-based WebP detection | Native `image-set()` / `<picture>` | ~2020 | Zero JS overhead |
| `loading="lazy"` on all images | `fetchpriority="high"` + `loading="eager"` on LCP | ~2022 | Direct LCP improvement |
| `<link rel="preload" href="single.jpg">` | `<link rel="preload" imagesrcset="...">` | Chrome 73+, all modern browsers | Preloads size-appropriate variant |

**Deprecated/outdated:**
- Modernizr-based WebP detection: replaced by native `<picture>` and `image-set()`
- `@astrojs/image` integration: merged into core Astro assets in Astro 3.x; but irrelevant here since images are in `public/`

1. **Hero preload in BaseLayout.astro vs HeroSection.astro slot**

   - What's unclear: Whether the plan should add a head slot (cleaner architecture) or hardcode the preload in BaseLayout
   - Recommendation: Since this is a single-page site, hardcode directly in BaseLayout. The LCP optimization is global and unconditional.

2. **Srcset width accuracy for requirements**
   - What we know: Requirements specify "640w/1280w/2048w" but source is only 1600px wide
   - What's unclear: Whether the requirement literally means 2048w files or "three sizes up to 2048"
   - Recommendation: Use 640w/1280w/1600w (accurate to source) and document that 1600w is the effective maximum. Don't advertise 2048w in the srcset when the file is 1600px wide.
