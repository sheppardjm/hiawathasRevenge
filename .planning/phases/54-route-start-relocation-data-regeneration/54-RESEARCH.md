## Summary

Phase 54 is a data-accuracy refresh: same course footprint, new start/finish staging point (~2 km SW of old start at 46.34770, -86.72515). The three alt-start GPX files already exist in `~/Downloads` (dated 2026-05-29 10:34) and have been verified to start exactly at the target coordinate. The pipeline is fully understood — it is an 11-step Node.js script that processes GPX to JSON, snaps sectors and restocks by coordinate, derives elevations, and copies GPX files to `public/`.

Three of the seven requirements are trivially satisfied by replacing the GPX files and re-running the pipeline: sector snapping (ROUTE-03) and restock mileages (ROUTE-04) are fully coordinate-driven and need no config changes, and GPX downloads (ROUTE-07) work transparently if we replace files in-place using the existing filenames.

Two issues require targeted fixes before or alongside the pipeline run. First, `match-photos.js` contains a staleness bug: it reads `public/data/route-data.json` (a legacy path from Phase 02 that is no longer regenerated by the pipeline) instead of `public/data/100mi/route-data.json`. This must be fixed before the pipeline run so photo map coordinates snap to the correct new route geometry. Second, all 56 entries in `public/data/photos-manifest.json` have mileage tags calibrated to the old course and need to be shifted by approximately +1.59 miles (with modular wrap-around at ~101.91 for the 5 near-end photos). The planner should include a migration script task for this rather than requiring manual edits to all 56 entries.

**Primary recommendation:** Replace GPX files in-place (keep existing filenames), fix the match-photos.js path bug, run a mileage-shift migration script on photos-manifest.json, run `npm run pipeline`, then verify pipeline output and do a smoke-test build.

## Common Pitfalls

### Pitfall 1: Stale `public/data/route-data.json` (match-photos.js legacy bug)
**What goes wrong:** After pipeline runs, `match-photos.js` reads `public/data/route-data.json` (a static legacy file from Phase 02, identical to the old 100mi route, NOT regenerated). Photo lat/lon coordinates in `photos.json` are snapped to the OLD route geometry even though `photos-manifest.json` has been updated to new mileages.
**Why it happens:** `match-photos.js` line 23 hardcodes `const ROUTE_PATH = resolve(ROOT, 'public', 'data', 'route-data.json')` — a path that was correct before the multi-route refactor (Phase 33) moved route data to per-route subdirectories. The file exists (committed) but is stale.
**How to avoid:** Fix line 23 to: `const ROUTE_PATH = resolve(ROOT, 'public', 'data', '100mi', 'route-data.json')`. This must be done BEFORE the pipeline run.
**Warning signs:** `public/data/photos.json` entries have lat/lon values that appear near old start coordinate (46.364xx) rather than the new course geometry.

### Pitfall 2: Photo mileage wrap-around at route end
**What goes wrong:** The mileage shift is +1.59 miles. Five photos in `photos-manifest.json` have mileages 99.0–100.3, which shift to 100.59–101.89. Since the new total is ~101.91 miles, these are valid but close to the limit. If any math rounds up past the total, `snapByMileage` in match-photos.js will snap to the very last route point.
**Why it happens:** Loop rotation puts the old finish area very close to the new finish (they're only ~1.59 miles apart on the loop). The wrap is natural, not a bug.
**How to avoid:** Migration script must use `% newTotalMiles` modulo arithmetic. Test that no resulting mile value exceeds `newTotalMiles` after shift.
**Warning signs:** Multiple photos cluster at the exact same lat/lon as the last route point.

### Pitfall 3: elevationTargetRange miss on new 100mi track
**What goes wrong:** `parse-gpx.js` iterates `THRESHOLDS_TO_TRY = [2, 1, 3, 1.5, 2.5, 4]` and uses the first threshold whose gain (ft) falls in `elevationTargetRange = [2123, 2411]`. If no threshold lands in range, the script uses the threshold=4 result by default (exhausting the list without setting ELEVATION_THRESHOLD_METERS from the loop).
**Why it happens:** The new alt-start track is a RidewithGPS export (2676 pts vs old Munising 1927 pts) — same course but different GPS sampling may produce slightly different elevation gain figures. Same course footprint means the range should still be valid, but verify.
**How to avoid:** Read the pipeline log output carefully. If "IN RANGE" does not appear, update `elevationTargetRange` based on the logged threshold values that are closest to the expected gain.
**Warning signs:** Pipeline log for 100mi shows no "IN RANGE" annotation across all threshold scans.

### Pitfall 4: Photo mileage tags calibrated for wrong route total
**What goes wrong:** The migration script assumes new total is 101.91 miles (computed from raw GPX haversine). After RDP simplification in parse-gpx.js, the "last simplified point" mileage will be slightly different (the simplified set's last retained point may be before the exact end).
**Why it happens:** `parse-gpx.js` computes mileage on the full-resolution set, then retains the mileage of the last SIMPLIFIED point as `totalMiles`. This is the canonical total.
**How to avoid:** Compute the modulo divisor AFTER running the pipeline (read `public/data/100mi/route-data.json` meta.totalMiles). The migration script for photos-manifest.json should be written to accept the true post-pipeline total as a parameter, or designed so the admin UI can handle minor out-of-range values gracefully (snapByMileage clamps to nearest anyway).
**Warning signs:** Pipeline logs show totalMiles significantly different from 101.91 (e.g., <100 or >103).

### Pitfall 5: Sector `endIdx <= startIdx` on rotated course
**What goes wrong:** `resolve-annotations.js` has a guard: if `endSnap.snapIdx <= startSnap.snapIdx`, it sets endIdx to `routePoints.length - 1`. On the rotated course, sectors that previously spanned normally might have their coordinate snap land on a wrong index if there's any route shape ambiguity near the start/end area.
**Why it happens:** The 520 sector starts very close to the new staging point (sector-520 startLat=46.35686 is ~1.5 km from the new start). After rotation, mile 0 is at the new start and the 520 sector will appear at approximately mile 1-2 (previously miles 1.1-2.4). The haversine snap should still work correctly, but the index ordering must be verified.
**How to avoid:** Pipeline already logs "Index check: all startIdx < endIdx - OK" — read this log output and fail the plan task if it doesn't appear.
**Warning signs:** Pipeline logs an "ERROR: {sector-id} startIdx >= endIdx" message.

### Pitfall 6: `Hiawatha_100.gpx` confusion
**What goes wrong:** A file named `Hiawatha_100.gpx` already exists at the repo root (22,992 point high-res Garmin recording of the OLD start — starts at 46.363, not 46.347). Someone accidentally uses it instead of the alt-start file.
**Why it happens:** The filename suggests it's the 100mi route, and it's at the repo root. It was never referenced in route-config.js and was committed in Phase 03-02 (then reverted). It remains as an unused artifact.
**How to avoid:** The 100mi replacement target is `Munising_Hiawatha_s_Revenge.gpx`, NOT `Hiawatha_100.gpx`. The source is `~/Downloads/Hiawatha's Revenge 100 (alt start).gpx` (2676 pts, starts at 46.3477, -86.7251). Verify with first-point coordinate check.
**Warning signs:** parse-gpx.js log shows `22992 raw track points` for 100mi (that's the old Garmin recording size, not the new alt-start count of 2676).

## Photo Mileage Migration — Technical Details

[ASSUMED: The rotation offset is approximately +1.59 miles based on haversine analysis of old start position on new alt-start course.]

The migration script logic:

```javascript
// Source: research computation on ~/Downloads/Hiawatha's Revenge 100 (alt start).gpx
// Old start at new-course mile 100.32; new total ~101.91
// offset = 101.91 - 100.32 = 1.59 miles

const NEW_TOTAL_MILES = 101.91; // approximate — update to meta.totalMiles after pipeline
const OFFSET_MILES = 1.59;      // old course mile 0 is at new course mile 100.32

function shiftMile(oldMile) {
  let newMile = oldMile + OFFSET_MILES;
  if (newMile > NEW_TOTAL_MILES) {
    newMile = newMile - NEW_TOTAL_MILES;
  }
  return Math.round(newMile * 10) / 10;
}
```

**Verification:** After migration, the photo at old mile 44.7 (near Camp 7 Lake, which is at actual GPS coord) should map to approximately 46.3, and the photo at old mile 75.7 (near Midway) should map to approximately 77.3. These can be spot-checked against the post-pipeline annotations.json restock snap mileages.

**Important:** The `NEW_TOTAL_MILES` constant should ideally be set from `public/data/100mi/route-data.json` meta.totalMiles AFTER the pipeline runs. Since the migration must happen BEFORE the pipeline run (pipeline reads photos-manifest.json via match-photos.js), use the pre-computed approximate value (101.91). The error margin is small (<0.1 mi) and snapByMileage will clamp gracefully.

Actually, there is a sequencing choice:
- Option A: Run migration script THEN pipeline (photos-manifest updated before match-photos runs)
- Option B: Fix match-photos.js path bug THEN run pipeline THEN migration THEN pipeline again

**Recommendation:** Option A — update photos-manifest.json first, then fix match-photos.js path, then run pipeline once. This is cleaner and avoids running the pipeline twice.
